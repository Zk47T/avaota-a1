# A733 DRAM training: what the vendor code does, and how to freeze it and read it

Target: Allwinner A733 (Orange Pi Zero 3W / Zero 4), LPDDR5.

Status on 2026-10-28:
- Everything here comes from Allwinner's and Orange Pi's own public binaries, compared with NXP's open i.MX95 code.
- Every number is regenerated by `scripts/analyze.py`.
- Nothing has run on an A733 yet. Hardware steps are marked **(untested)**.

## Verdict

**The A733 is a better DDR-training learning board than its price suggests.**

- **It's the same PHY as your i.MX95:**
  - the Synopsys DWC LPDDR5/4X PHY with its PMU training firmware;
  - the same CSR map (IMEM `0x50000`, DMEM `0x58000`, mailbox in `0xD00xx`);
  - the same message-block layout (Allwinner's defaults match NXP FW2024.09 word for word in several places);
  - Allwinner's trained-state register list shares **5,671 of 5,698** registers with NXP's i.MX95 LPDDR5 trained-CSR list (99.5%).

  So what you learned on the i.MX95 transfers register for register.
- **The vendor DRAM driver ships unstripped.** Its function names are the Synopsys PhyInit steps (`C_initPhyConfig` … `I_loadPIEImage`).
- **Allwinner already "freezes" training state in three places** (section 3): a 2D-result save in boot0, a full PHY-state retention for suspend in the ARISC firmware, and crash-dump-to-FEL.
- **Black box, same as on NXP:** the PMU training firmware itself, and the string table for its streaming debug messages.
- **Missing compared with NXP:** a vendor DDR config/stress tool, a public QuickBoot firmware image, and source code. On the plus side: about $60, FEL recovery (unbrickable), and 2.4 GHz LPDDR5.

## 2. The training flow (from the disassembly)

`dram_para` word *n* is at byte offset 4*n*. Field names are SyterKit's `SUNXI_DRAM_PARAM_V2`.

```c
init_DRAM(dram_para):
  if (type == LPDDR4 && !(tpr1 & BIT31) && !(tpr10 & BIT29))
      para[32..49] = tpr6[6:0] x 4 bytes; para[50] = mr14 x 4     // default seeds
  dram_vol_set();
  if (!(tpr13 & BIT0)) auto_scan_dram_config();                 // first boot: size/rank/width
  mctl_core_init() -> mctl_phy_init():
      for each P-state (DFS frequencies):
          C_initPhyConfig, D_loadIMEM (0x50000), E_setDfiClk, F_loadDMEM (0x58000),
          G_execFW  (PMU runs training, 1D + 2D)                // "DRAM Pstate %d training"
          I_loadPIEImage
      if (!(tpr10 & BIT29)) replay para[32..49] into PIE memory (CSR 0xA0D68..0xA0DF6)
  if (!(tpr1 & BIT31) && (tpr10 & BIT29)) {
      save_phy_2d_training_result():
          para[32..49] <- DBYTE0-3, lanes 0-8, CSR 0x1x04E / 0x1x04F (7-bit values)
          para[50/51]  <- LPDDR5 MR14 / MR15 (DRAM VREF DQ), ch0/1 x rank0/1, via MR16 FSP switch
      if (!(tpr10 & BIT30)) tpr10 &= ~BIT29;                   // one-shot unless BIT30
  }
  dramc_simple_wr_test(); return size;
```

The PMU firmware does the actual training on every boot. Allwinner's "save" keeps a small result set: per-lane Vref-like bytes plus the DRAM-side VREF(DQ). Later stages reuse it as seeds and in PIE sequences, rather than skipping training the way NXP's QuickBoot does.

## 3. Three vendor ways to freeze state and read it later

| | What is frozen | Where it goes | How to read it |
|---|---|---|---|
| **A. boot0 2D save** (`tpr10.29`, on in Orange Pi's Zero 3W firmware) | per-lane 7-bit values (DBYTE CSR `0x1x04E/F`) and MR14/MR15 | `dram_para[32..51]` in boot0's RAM copy, handed on | JTAG: read the para buffer after `init_DRAM`; or the UART trace (section 4B) |
| **B. ARISC standby retention** | DRAM in **self-refresh**; **5,717 PHY CSRs** (DBYTE 4×307, MASTER 228, AC 2×42, ACSM 2,712, PIE 1,371, DRTUB 73, …) saved on the first suspend and restored on resume (no retraining) | ARISC SRAM `save_data` | `echo mem > /sys/power/state` once, then read ARISC SRAM (address `[?]`), or JTAG the ARISC (S-RJTAG on PM0/PM1) `[?]` |
| **C. Crash dump** | the whole DRAM content after a kernel panic | stays in DRAM; boot0 brings DRAM up and jumps to FEL | needs `CONFIG_AW_CRASHDUMP` plus the monitor (ATF) side. Then TigerDump or `xfel read`. Training patterns overwrite a small DRAM region; the rest survives if DRAM stayed refreshed `[?]` |

B is Allwinner's version of NXP's QuickBoot (`ddrphy_qb_state`: `csr[5168]`, `acsm[4K]`, per-P-state data, `0x200` MSB). It's the same register set, used for resume rather than cold boot.

## 4. Our freeze: step and snapshot the training

**4A. JTAG (live, CPU not halted)** `(untested)`

1. **Get JTAG during DRAM init.** Pick one route:
   - **PB route, booting from SD:**
     ```
     scripts/boot0_tool.py patch boot0_sdcard_orangepizero3w.fex out/boot0_jtag.fex --jtag 1
     sudo dd if=out/boot0_jtag.fex of=/dev/sdX bs=1k seek=8 conv=notrunc,fsync
     ```
     Wire the CH347F to PB0 TMS, PB1 TCK, PB2 TDO, PB3 TDI, GND, VTref 3.3 V. This only changes `enable_jtag` and the checksum.
   - **FEL route (no SD card):** `xfel write32 0x02000100 <(read & ~0xffff) | 0x7777>` for PB, or `0x02000300` → `0x0f3f3f33` for the SD-sniffer pins. Then run SyterKit's `init_dram` FEL app.
2. Start OpenOCD:
   ```
   openocd -f interface/ch347.cfg -f src/syterkit/scripts/openocd/allwinner_a733.cfg -f scripts/a733-ddr.tcl
   ```
   You need OpenOCD master (CH347 + ADIv6).
3. Commands (`scripts/a733-ddr.tcl`):
   - `phy_rd`/`phy_wr` work through the AHB-AP, so no core is halted.
   - `a733_hdtctrl 0xfe` raises the PMU message level. Call it after `F_loadDMEM` and before `G_execFW`. That's easiest with a breakpoint on `dwc_ddrphy_phyinit_G_execFW`, using the SyterKit ELF symbols.
   - `a733_train_trace {0x02 0x05}` reads every mailbox message, decodes streaming messages and their arguments, and **stops without acking** at the listed stages. The PMU then waits; that's the freeze. Call it again to continue. The vendor `G_execFW` then sees the final message.
   - `a733_freeze` / `a733_thaw` (**experimental**): stall the PMU and take the CSR mux to read mid-training state. Synopsys doesn't document this, so expect to rerun the training.
   - After 0x07: `a733_dmem_dump` (message block with the training results) and `a733_dump_trained out/lpddr5_retention_csrs.txt` (the full 5,717-CSR snapshot, same set as ARISC/QuickBoot).
4. Check without hardware: the mailbox logic was run against a simulated PMU: stage, streaming plus arguments, freeze at 0x05, resume, PASS.

**4B. UART trace, no JTAG** `(untested)`

SyterKit's FEL app `soc/sun60iw2/app_efex/init_dram` links Allwinner's `libdram`.

1. Make the vendor function weak:
   ```
   arm-none-eabi-objcopy --weaken-symbol=dwc_ddrphy_phyinit_G_execFW soc/sun60iw2/lib/libdram-lpddr5.a
   ```
2. Add `scripts/syterkit/g_execfw_trace.c` to the app.

What the replacement does:
- uses the vendor's exact register sequence;
- sets `HdtCtrl` (default `0xFE`; `-DA733_HDTCTRL=0x05` for detailed messages);
- prints every mailbox message, including streaming arguments;
- dumps 0x200 DMEM words after training;
- returns the same value the vendor caller checks (`== 7`).

Checks so far:
- It compiles warning-free for Thumb with clang 14.
- `llvm-objcopy --weaken-symbol` turns the vendor definition into `W`.
- Its logic passed a host-side simulation of the PMU mailbox.

**Experiments this enables**

1. Compare trained CSRs at 1800 vs 2400 MHz: Orange Pi ships both boot0 images.
2. Repeat at cold vs hot board temperature, and run-to-run, to see which registers move.
3. Compare A733 trained values with your i.MX95 snapshot, register for register.
4. Suspend/resume: confirm "the first time ddr standby" on the first suspend only, and no retraining after.
5. Raise `HdtCtrl` and map streaming IDs against what you decoded on the i.MX95: same PHY generation, possibly the same firmware branch `[?]`.

**Upstream angle.** No open A733 DRAM init exists anywhere. Yixun Lan's U-Boot "initial A733 support" (v3, January 2026) stops before DRAM, which blocks a mainline boot (main README 3.11). The material here makes a U-Boot SPL driver realistic:
- the PHY map, mailbox and message block;
- the training flow;
- the `dram_para` decode for the Zero 3W.

Model it on U-Boot's `drivers/ddr/imx/phy` (same Synopsys PHY family), with the PMU firmware as an external binman blob.

## 6. Unknowns `[?]`

- That `0x58009` low byte is HdtCtrl and `0x58008` is SequenceCtrl. Inferred from NXP's values at the same addresses; confirm against your i.MX95 notes.
- Whether PB0–PB3 reach the Zero 3W / Zero 4 40-pin header. The DT uses them for UART2/I2C0, which Orange Pi normally routes to the header.
- The ARISC SRAM address of `save_data`, and whether Linux can read it via `/dev/mem`.
- Whether the crash-dump path keeps DRAM refreshed across the reset, and which region the training patterns overwrite.
- Whether the A733 PMU firmware is the same build as NXP FW2024.09. The IMEM sizes and message-block defaults are close, but the version field hasn't been compared yet.
